The settings module is the central configuration surface for the entire application, and it has grown over time into a fairly elaborate system with many interacting parameters. The core idea is simple: when some part of the program needs a configuration value, it calls a retrieval routine with a key, and that routine first checks whether an explicit override has been supplied before falling back to a documented default. What follows is a thorough tour of the many defaults the module ships with, along with the reasoning behind each choice. Throughout, the exact configuration key names are given in backticks so there is no ambiguity about what string to use.

Let us begin with the behavior around retrying operations, which is surprisingly nuanced. The system distinguishes between several different notions of retrying. The most general one, `max_retries`, governs how many times an ordinary failed operation is attempted again, and its default is set to 5. Separately, `max_retry_delay` controls the delay between those attempts, expressed in milliseconds, and it defaults to 250. The growth factor applied to that delay on each successive attempt is `max_retries_backoff`, which defaults to 2. Note that connection establishment is treated as its own concern: `connection_max_retries`, the number of times the system will retry merely opening a connection, defaults to 3, deliberately lower than the general count. There is also a distinct notion for whole requests, `request_max_retries`, which defaults to 4.

Timeouts are similarly layered, and it is worth being careful about which is which. The setting `read_timeout`, the time the system waits while reading data from an already-open connection, defaults to 30. The setting `connect_timeout`, the time it waits merely to establish the connection, is shorter, defaulting to 10. Connections that sit unused are reclaimed after `idle_timeout`, which defaults to 600. At a lower level, `socket_timeout` defaults to 15, and the initial protocol handshake window `handshake_timeout` defaults to 5.

The caching subsystem has its own family of knobs. The setting `cache_max_entries`, the maximum number of entries the cache holds before evicting, defaults to 1024. Each entry is fresh for a time-to-live `cache_ttl_seconds`, defaulting to 3600. There is a floor as well: `cache_min_entries` defaults to 16. When eviction occurs it happens in groups, and `cache_eviction_batch` defaults to 32.

Connection pooling introduces yet another set of related values. The setting `pool_min_size` keeps a minimum number of connections open and defaults to 2, while `pool_max_size` caps the pool and defaults to 20. Beyond that maximum, `pool_overflow` permits temporary extra connections, defaulting to 10. Connections are periodically recycled on the schedule `pool_recycle_seconds`, defaulting to 1800.

A handful of size-related parameters govern data movement and pagination. The `buffer_size` defaults to 8192, while the streaming `chunk_size` defaults to 4096. For paginated results, `max_page_size` defaults to 100, and `default_page_size` defaults to 25.

Finally, a few operational parameters round out the configuration. The logging verbosity `log_level` defaults to the string warning. Log files rotate once they reach `log_max_bytes`, defaulting to 1048576. The application runs a pool of workers whose count `worker_count` defaults to 8. The internal work queue `queue_max_depth` holds up to 512 items by default. A periodic heartbeat is emitted on the interval `heartbeat_interval`, defaulting to 45. And when asked to shut down, the application allows `shutdown_grace_period`, defaulting to 60, for in-flight work to finish.

Any key not among those described above, and for which no override has been supplied, yields None.
